# Sección 4.2 Diagramas: textos para pegar debajo de cada figura

Convención de todas las figuras: los elementos con borde sólido están implementados en el monolito del primer parcial; los elementos grises con borde punteado están diseñados, pero su implementación corresponde a parciales posteriores.

**Figura X. Diagrama de contexto.** Muestra la plataforma como un solo sistema y a quienes interactúan con ella. Los siete roles del sistema usan la aplicación web, cada uno con una función distinta en el proceso de devolución. Proveedores, tiendas y transportistas no se conectan al sistema: se registran como catálogos para ligar cada devolución con su lote, su punto de venta y la ruta por la que se recolectó, que es la información que permite el análisis de causa raíz. El sistema se ejecuta en Google Cloud Platform. El almacenamiento de archivos en Google Cloud Storage está diseñado, pero todavía no se implementa.

**Figura X. Diagrama de contenedores.** En el primer parcial la plataforma se compone de tres contenedores orquestados con Docker Compose dentro de una VM de Compute Engine. El contenedor devoluciones_app ejecuta el monolito Flask con Gunicorn. El contenedor devoluciones_postgres guarda la información transaccional y aplica reglas de negocio mediante triggers. El contenedor devoluciones_redis conserva las sesiones, los intentos fallidos y el bloqueo temporal. Los datos de PostgreSQL y Redis persisten en volúmenes de Docker. Los microservicios, MongoDB, el bucket y las aplicaciones móvil y de escritorio aparecen punteados porque en este parcial solo están diseñados, como lo pidió la instrucción de la entrega.

**Figura X. Diagrama de componentes.** Describe la organización interna del monolito según el patrón MVC. Cada blueprint de Flask corresponde a un módulo del negocio y actúa como controlador: acceso y administración (auth, usuarios, catálogos), proceso de devolución (ventas, devoluciones, logística, inspecciones, reembolsos) y análisis y monitoreo (panel y /health). Las vistas son plantillas Jinja2. Los servicios transversales concentran la seguridad (security.py verifica rol y permiso sobre el recurso y registra la bitácora), el acceso a datos con parámetros ligados contra inyección SQL (db.py), el control de intentos de acceso (cache.py) y la configuración tomada de variables de entorno (config.py).

**Figura X. Diagrama de despliegue.** Los integrantes escriben el código en sus equipos y lo publican en GitHub. En la VM de Compute Engine (CentOS con SELinux en modo Enforcing) se obtiene con git pull y se monta en el contenedor de la aplicación. Docker Compose levanta la aplicación, PostgreSQL 16 y Redis 7. Las credenciales se leen del archivo .env, que existe solo en la VM y nunca se sube al repositorio. Una regla del firewall de GCP permite el tráfico al puerto 8000 de la aplicación.

**Figura X. Diagrama de red.** El único puerto expuesto a internet es el 8000 de la aplicación, permitido por la regla de firewall de GCP. PostgreSQL y Redis no son accesibles desde fuera: la aplicación se comunica con ellos por la red interna de Docker usando los nombres de servicio postgres y redis. Sus puertos solo se publican en 127.0.0.1 (55432 y 56379) para administrarlos desde la propia VM, y se usan puertos no estándar porque la VM ya tiene un PostgreSQL nativo en el 5432. Queda pendiente habilitar HTTPS (RNF-14), porque hoy el tráfico viaja por HTTP.

**Figura X. Diagrama de secuencia del proceso principal.** Recorre una devolución de principio a fin sobre PostgreSQL. El cliente consulta su venta y registra la solicitud ligada a una línea de venta, con lo que se genera un folio único. El analista autoriza, rechaza o solicita información. El coordinador programa la recolección con ruta y transportista. El encargado del centro confirma la recepción. El inspector registra el estado físico y la cadena de frío, y el analista decide la disposición. El encargado de reembolsos registra el reembolso. Cada paso cambia el estado de la devolución y queda en la bitácora, y los triggers de la base impiden enviar a inventario un producto no apto o reembolsar sin autorización.

**Figura X. Diagrama de comunicación entre aplicaciones.** En el primer parcial, el navegador se comunica con el monolito por HTTP con páginas HTML generadas en el servidor. El monolito usa SQL parametrizado hacia PostgreSQL y el protocolo RESP hacia Redis. El endpoint /health responde en JSON con el estado de ambas dependencias. Para los parciales posteriores está diseñado que la aplicación móvil consuma JSON y la de escritorio XML, a través de APIs REST versionadas y protegidas con JWT, detrás de las cuales operan los microservicios, MongoDB y el bucket.

**Figura X. Diagrama de autenticación.** El inicio de sesión valida la contraseña contra su hash y registra cada intento en PostgreSQL. Los intentos fallidos se cuentan en Redis con una expiración de 15 minutos; al quinto intento la cuenta se bloquea temporalmente y el mensaje de error es genérico para no revelar si el correo existe. Con credenciales correctas, la sesión se guarda en Redis y el navegador recibe una cookie firmada HttpOnly. En cada petición posterior se verifica el rol (roles_required) y, en expedientes, que el recurso pertenezca al usuario (devolucion_visible). Los accesos denegados quedan en la bitácora. JWT, token de renovación y revocación en Redis están diseñados para las APIs del segundo parcial.

**Figura X. Diagrama de almacenamiento de datos.** Distribuye la información según su naturaleza. PostgreSQL guarda los datos transaccionales y aplica las reglas de negocio con llaves foráneas, restricciones UNIQUE, triggers y eliminación lógica. Redis guarda datos temporales con expiración: sesiones, contadores de intentos y bloqueos. MongoDB, en diseño, guardará el detalle variable de las inspecciones, los metadatos de evidencias, los eventos y los resultados del análisis de causa raíz. El bucket de Cloud Storage, también en diseño, guardará fotografías y documentos. La columna mongo_doc_id y los campos bucket y objeto ya existen en PostgreSQL, así que habilitar ambos no requerirá migrar datos.
